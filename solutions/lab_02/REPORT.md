### Практическая задача: независимые конфигурации

Для конфигурации со вложенными изменяемыми списками простого присваивания недостаточно: обе переменные будут ссылаться на один словарь и его содержимое. Для независимой копии подходит `copy.deepcopy()`.

```python
import copy

config1 = {
    "name": "Учебный проект",
    "participants": ["Глеб", "Аким"],
    "par": [[1], [2]]
}
config2 = config1

config2["participants"].append("Саня")
print("После изменения через alias:")
print(config1)
print(config2)
assert config1["participants"] == config2["participants"]

config3 = copy.deepcopy(config1)
config3["participants"].append("Виктор")
config3["par"].append([3])

assert "Виктор" not in config1["participants"]
assert [3] not in config1["par"]
print("\nНезависимая конфигурация:")
print(config1)
print(config3)
```

Ожидаемый результат: изменения `config_2` отражаются в `config_1`, поскольку это один объект. Изменения `config_3` не влияют на `config_1`, потому что вложенные изменяемые объекты скопированы.

## Задание 3. Подсчет ссылок и время жизни объекта

**Код**
```python
import sys

data = [1, 2, 3]
print("После создания:", sys.getrefcount(data))

alias = data
print("После создания alias:", sys.getrefcount(data))

container = [data]
print("После помещения в контейнер:", sys.getrefcount(data))

del alias
print("После del alias:", sys.getrefcount(data))

container.clear()
print("После очистки контейнера:", sys.getrefcount(data))
```

- `sys.getrefcount()`, сама функция создает еще одну временную ссылку на этот объект в процессе выполнения.
- `data = [1, 2, 3]`, `alias = data`, `container = [data]`, `sys.getrefcount(data)` - при создании новой переменной создается новая ссылка на объект, счетчик растет, также при вызове функции счетчик увеличивается на 1.
- `del alias`, `container.clear()` - `del` удаляет имя `alias`, то есть ссылку на объект, `clear` удаляет ссылку для всех объектов, которые были внутри.
- Инструкция `del` удаляет имя (переменную), а не сам объект в памяти.

**Код**
```python
import weakref


class Record:
    pass


record = Record()
weak_record = weakref.ref(record)

print(weak_record())
del record
print(weak_record())
```

**Объяснение:**\
Слабя ссылка не учитывается в счетчике объекта, и если он достигнет 0, то объект спокойно удалится.\
Пример: Кэширование данных, когда мы хотим временно сохранять тяжелые объекты в памяти, но не хотим, чтобы этот кэш мешал их удалению, когда они больше не нужны в основной программе.

### Практическая задача: реестр слабых ссылок

```python
import weakref


class Record:
    pass

registry = weakref.WeakValueDictionary()

first = Record()
second = Record()

registry["first"] = first
registry["second"] = second
registry["third"] = Record()

print("Исходный реестр:", list(registry.keys()))

print("Первый объект существует:", "first" in registry)
print("Второй объект существует:", "second" in registry)
print("Третий объект существует:", "third" in registry)

del first

print("\nПосле удаления первой сильной ссылки:")

```

First и second имеют сильные ссылки в переменных, поэтому живут. Для третьего объекта сильная ссылка нигде не сохраняется: после добавления в WeakValueDictionary он сразу уничтожается, и запись исчезает.

### Итоговый анализ
### 1. Отказ от избыточного глубокого копирования и использование ссылочной модели
- **Суть метода:** Избегать автоматического применения полного дублирования данных (`copy.deepcopy()`). Вместо создания независимых копий тяжелых объектов следует использовать передачу по ссылке, либо выполнять точечное копирование только изменяемых конфигурационных слоев.
- **Связь с экспериментом:** В **Задании 2** эксперимент наглядно показал, что `deepcopy()` рекурсивно дублирует абсолютно все объекты внутри структуры, что приводит к лавинообразному выделению памяти. В то же время **Задание 1** продемонстрировало, что неизменяемые объекты (такие как строки и числа) при присваивании (`b = a`) безопасно разделяют один и тот же адрес в памяти (`id`), не создавая накладных расходов, пока не потребуется их модификация.

### 2. Замена динамических списков фиксированными контейнерами (кортежами или слотами)
- **Суть метода:** Для хранения больших неизменяемых наборов данных вместо списков (`list`) следует использовать кортежи (`tuple`). Это избавляет программу от избыточного выделения памяти "на вырост".
- **Связь с экспериментом:** В **Задании 5 (Часть 1 и 2)** мы исследовали размеры объектов и динамику роста списков. Эксперимент показал, что кортеж из 10 элементов занимает меньше памяти, чем аналогичный список (120 байт против 136 байт). Более того, изучение стратегии аллокации `list.append()` показало, что списки резервируют до 30-50% лишней памяти «с запасом» (over-allocation) для обеспечения скорости $O(1)$. На масштабах в миллионы объектов этот пустой резерв превращается в гигабайты зря потраченной RAM.

### 3. Своевременное разрушение циклических ссылок и явное управление временем жизни (Слабые ссылки)
- **Суть метода:** Проектировать структуры данных (графы, деревья, кэши) без жестких циклических зависимостей, либо разрывать их с помощью модуля `weakref`. Это позволяет объектам удаляться мгновенно через подсчет ссылок, не дожидаясь тяжелого и непредсказуемого по времени цикла работы сборщика мусора.
- **Связь с экспериментом:** В **Задании 4** эксперимент с графом наглядно доказал, что объекты с циклическими ссылками остаются в памяти даже после удаления всех внешних имен (`del`). Их очистка возможна только через `gc.collect()`. В свою очередь, **Задание 3** показало, что реестры на основе слабых ссылок позволяют CPython удалять объекты из памяти немедленно в момент падения счетчика сильных ссылок до нуля. Это гарантирует своевременный возврат ресурсов и предотвращает скрытые утечки памяти.

### Практическая задача: единый отчёт о памяти
```python
import sys
import tracemalloc

def measure(name, factory, n=100_000):
    tracemalloc.start()
    obj = factory(n)
    current, peak = tracemalloc.get_traced_memory()
    size = sys.getsizeof(obj)
    tracemalloc.stop()
    return {
        "Название сценария": name,
        "Число элементов": n,
        "Размер внешнего объекта": size,
        "Текущий объем выделенной памяти": current / 1024,
        "Пиковый объем выделенной памяти": peak / 1024,
    }

results = [
    measure("list()", lambda n: list(range(n))),
    measure("tuple()", lambda n: tuple(range(n))),
]

for result in results:
    print(
        f"Название сценария: {result['Название сценария']}\n"
        f"Число элементов: {result['Число элементов']}\n"
        f"Размер внешнего объекта: {result['Размер внешнего объекта']} B\n"
        f"Текущий объем выделенной памяти: {result['Текущий объем выделенной памяти']:.2f} KB\n"
        f"Пиковый объем выделенной памяти: {result['Пиковый объем выделенной памяти']:.2f} KB\n"
    )

if results[1]["Пиковый объем выделенной памяти"] > 0:
    print("Отношение пиков list/range:",
          f"{results[0]['Пиковый объем выделенной памяти'] / results[1]['Пиковый объем выделенной памяти']:.2f}")
```

## Заключение
В ходе работы рассмотрены связи между именами и объектами, различия между присваиванием, поверхностным и глубоким копированием, подсчёт ссылок и циклическая сборка мусора. Эксперименты показывают, что присваивание не создаёт копию объекта, поверхностная копия разделяет вложенные объекты, а глубокая копия предназначена для независимого дублирования вложенных изменяемых структур. Слабые ссылки позволяют хранить ссылки на объекты без продления их времени жизни. Для анализа памяти полезны `sys.getsizeof()` и `tracemalloc`, однако их результаты зависят от версии CPython, платформы и окружения запуска.
